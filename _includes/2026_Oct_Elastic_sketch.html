The Stream Counting Problem

Interactive Exercise: Track counts of incoming items on the fly!

△ ○ □ △ ★ △ ○ □ △

  • Massive Stream ($M \to \infty$): Items drawn from universe $\mathcal{I}$ of size $n_{\mathcal{I}}$.
  • Strict Constraints: Sublinear memory $m \ll n_{\mathcal{I}}$, line-rate $O(1)$ per-item update time.

Top-K Heavy Hitters & Memory Trade-Off

  • Real-world workloads are skewed (Zipfian): a few "elephants" cause most traffic.
  • Counter-Based (Misra-Gries / Space Saving): Exact top-$k$ counts, but evictions are heavy; hard to handle deletions/turnstile streams.
  • Sketch-Based: Compact hash arrays; constant time updates, but hash collisions create estimation errors.

AMS & Count Sketch

AMS Sketch

Uses sign hash $s_j(i) \in \{-1, +1\}$.

Drawback: Updates ALL $m$ counters per item ($O(m)$ time).

Count Sketch

Hashing trick ($1$ bucket + $1$ sign per row); median estimator.

Drawback: Variance $\propto \|f\|_2^2$; elephants pollute mice.

Count-Min Sketch (CMS) & Its Flaw

  • $d \times w$ counter array with $d$ hash functions.
  • Query: $\hat{f}_i = \min_j C[j, h_j(i)]$. Fast $O(d)$ time, $O(1/\epsilon)$ space.
  • The Elephant Pollution Flaw: Elephant flows hash to counters shared with mice, blowing up small item estimates by $\|f\|_1$.

Elastic Sketch Architecture

Heavy Part ($m_1$ buckets)

Hash table tracking popular flows: (key, V+, V-, flag)

Light Part ($m_2$ counters)

Count-Min Sketch storing residual mouse flows.

Result: Elephants filtered into Heavy Part; Mice stay in Light Part!

Ostracism & Memory Interpolation

  • Ostracism Voting: Matching item $\to V^+ ++$; Mismatch $\to V^- ++$.
  • Eviction Threshold ($\lambda$): Evict if $V^- / V^+ \ge \lambda$.
  • Interpolation Spectrum:
    • $\lambda \to \infty$: Never evicts (fixed cache).
    • $\lambda \to 0$: Always evicts (pure Count-Min Sketch).

Addressing Classical Sketch Drawbacks

Tighter Error Bounds: Light Part error is bounded by $\epsilon \|f_L\|_1$ (residual stream) instead of $\epsilon \|f\|_1$.

  • Zero Error for Elephants: Heavy Part items with flag = False have exact counts.
  • Memory Savings: Light Part uses small 8-bit counters because elephant counts are removed.

Star-Shaped Markov Chain Model

  • Stationary Stream Model: $R_t \sim p = (p_1, \dots, p_{n_{\mathcal{I}}})$.
  • Heavy bucket dynamics map to an asymmetric random walk on a star graph:
    • Central Hub $0_b$: State when potential $U_b = \lambda V^+ - V^- = 0$.
    • Radial Branches: One branch per item $i$ hashing to bucket $b$.

Recurrence vs. Transience

Threshold parameter: $\lambda_i(\beta) = \frac{\mu_b - p_i}{p_i}$

Recurrent ($\lambda < \lambda_b^{(1)}$)

Elected items switch infinitely often $\to$ Heavy Part is unstable.

Transient ($\lambda > \lambda_b^{(1)}$)

Most popular item becomes permanently elected with prob $a_{i,\beta}(\lambda)$.

Limiting Error & Configuration

Limiting Expected Error ($d=1$):

$\mathbb{E}[\overline{\text{Err}}_\infty] = \frac{1}{m_2} (1 - \mathbb{E}_\beta[g_\beta(\lambda)])$

  • Optimal threshold: $\lambda^*(\beta) = O(n_{\mathcal{I}} / m_1)$ with high probability.
  • Search pruned to finite candidate set $\Lambda(m_1)$ ($\approx 20\text{--}30$ values), evaluable in $O(n_{\mathcal{I}})$ time!

Workload Skewness ($\alpha$) Insights

  • Higher Skewness ($\alpha \uparrow$, e.g., $1.2$ vs $0.8$):
    • A few dominant elephants take over the stream.
    • Optimal eviction threshold $\lambda^*$ decreases.
    • Heavy Part memory fraction $\gamma^*$ increases (e.g., $20\%$ vs $8\%$).
  • Highly skewed traffic demands more Heavy Part memory and lower eviction resistance!

Summary & Takeaways

  1. Hybrid Design: Elastic Sketch combines counter-based filtering with sketching via Ostracism.
  2. Collision Elimination: Elephant isolation drops estimation error from $\|f\|_1$ to $\|f_L\|_1$.
  3. Theoretical Grounding: Star-shaped Markov chains characterize exact limiting performance.
  4. Practical Tuning: Skewed workloads need larger Heavy Part allocations and lower $\lambda^*$.
